## サービス概要

- 三菱UFJ eスマート証券（旧 auカブコム証券）の個人向けAPI。**プログラムによる全自動取引は規約上OK**。
- 公式: https://kabu.com/item/kabustation_api/default.html ／ APIドキュメント: https://kabucom.github.io/kabusapi/
- 利用規定PDF: https://kabu.com/pdf/Gmkpdf/service/kabustationapiuserpolicy.pdf（**通読済み・2026-09-12**）

## 動作の前提（重要な運用制約）

- APIは**デスクトップアプリ「kabuステーション」経由**で動く（ローカルの `localhost:18080` 等にリクエスト）。
  → bot を動かすマシンで kabuステーションが常時起動している必要がある。
- **配置決定（2026-09-10）**: kabuステーションは **この Claude Code が動いている PC** にインストール済み（2026-09-12）。
  `daytrade-bot` も同じ PC で動かす。
  - ⚠️ 同じ PC で Claude Code が動いているが、**Claude / エージェントは bot の起動・停止、
    kabuステーションの操作、発注を一切しない**（CLAUDE.md 絶対ルール）。bot は社長がスケジュール実行する
    専用スクリプト。Claude はコードと日誌のドラフトのみ。
- **API有効化済み（2026-09-12）**: システム設定 > API で「APIを利用する」をON、本番用・検証用の
  APIパスワードを設定、「暗号化ログを出力する」もON（常時ONを推奨。障害・誤発注時の調査に必須）。

## 既知のリスク: kabuステーション障害時に無防備になる「隙間」（2026-09-12・社長との協議）

**逆指値（損切り）注文は、いったん証券会社のサーバーに受理されれば、そこで管理される。**
kabuステーションはあくまで「注文を出すための手元の窓口」であり、注文自体を保管している場所ではない。
つまり:

- 逆指値が**無事に発注・受理された後**なら、その後にkabuステーションやPCが落ちても、
  逆指値はサーバー側で生き続けて条件を満たせば執行される（＝落ちても致命的ではない）
- 本当に無防備になるのは、**「買い注文が約定してから、逆指値を出すまでのわずかな間」にkabuステーションや
  PCが落ちた場合**。この隙間の間は逆指値がまだ存在しないため、ポジションが無防備なまま放置される
- `guardrails.md`の「1日の最大損失額」によるbot側の監視も、**kabuステーションが落ちていれば同様に機能しない**
  （botの監視もkabuステーションAPI経由でしか状態を見られないため）。つまりこの隙間は、bot側の仕組みだけでは
  100%は埋められない

### 対策（3本柱。100%の自動防御は目指さず、隙間を減らし人に知らせる）

1. **隙間を短くする**: 買い約定後、間を置かずに逆指値を出す実装にする（entry→exit発注を可能な限り連続処理にする。
   kabuステーションAPIがエントリーと逆指値をセットで出せる注文方式（OCO等）をサポートしているかAPIドキュメントで確認する【要確認】）
2. **kabuステーションの監視・自動再起動**: 落ちたら検知してすぐ再起動する仕組みをPCに入れる（実装時に検討）
3. **人への通知を最終防衛ラインにする**: botからkabuステーションに接続できない状態が続いたら、
   社長に通知する（LINE通知・メール等）。異常時は自動で完全に守り切るのではなく、**「人に知らせて判断してもらう」**
   ところまでを設計のゴールにする

証券会社の規約でも「自作スクリプトの誤動作は当社は全部免責」（第4条5）となっており、この種のリスクは
利用者側が負う前提。100%自動でどんな障害にも対応できるとは考えず、上記の現実的な対策に留める。

## ソフトリミット（kabuステーション側のワンショット上限）— 重要な安全弁

システム設定 > API 画面に、**1回の注文で発注できる上限額をkabuステーション自身が強制的にブロックする機能**がある
（現状の設定: 現物300万円／信用300万円／先物100枚 等）。これはbotのコードにバグがあっても
超えられない**broker側のハード制限**であり、`guardrails.md` のソフトウェア上のガードレールとは別の
独立した安全弁になる。

- **推奨**: `guardrails.md` の「1トレードの投入額（委託保証金）」が確定したら、信用のソフトリミットを
  その額の**数倍程度の低い金額**（例: 投入額の3〜5倍を目安）に**下げる**。現状の300万円は初期設定のままで、
  v1（1日1銘柄・小さく始める想定）には大きすぎる。**万一botのコードが桁を間違えて発注しても、
  ここで機械的に止まる**ようにしておく、という考え方（多重防御）。
- 現物のソフトリミットも同様に、実際には使わない前提なら低めにしておいて問題ない。

## 検証用APIパスワード — 段階導入に使う

本番用と別に**検証用APIパスワード**が用意されている（ポート18081、本番は18080）。`strategy.md` の
段階導入（発注しないログモード → 最小ロット実発注）の間に、まずこの検証用環境で実際の発注コードパスを
動かして確認するステップを挟む。

### 実機確認結果（2026-09-13・`scripts/test_kabu_connection.py`で確認）

- **トークン取得（`POST /token`）・板情報取得（`GET /board`）・建玉一覧（`GET /positions`）は
  本番環境で実機確認済み。** レスポンスのフィールド名（`CurrentPrice`, `PreviousClose`,
  `OpeningPrice`, `Symbol` 等）はすべて想定通りだった
- **検証用環境（paper・ポート18081）の`board`は全項目nullを返す。** 市場データが検証環境に
  ミラーされていないため、「今の株価」を検証用環境から取得することはできない
- **示唆**: Stage B（発注コードパスの検証）は、**価格データを本番の`board`（読み取り専用・無害）から
  取得し、実際の注文（`sendorder`）だけを検証用に送る**というハイブリッド構成にする必要がある
  （本番トークンと検証用トークンを両方保持し、用途で使い分ける）
- **未検証のまま残っているのは`sendorder`（発注）のみ。** 次のステップはこれを検証用環境に対して
  実際に叩き、フィールド名・レスポンスを確認すること

## 認証・トークン

- トークンは**発行から24時間有効**、毎朝**6:15頃に自動リフレッシュ**。
- kabuステーションの終了・ログアウト・別トークン発行・早朝の強制ログアウトで**無効化**される。
  → bot は「トークン失効を検知したら再取得」する実装が必須。

## レート制限・発注件数の上限

- **発注API: 5件/秒**（情報・余力API等は10件/秒）
- ほかに**流量制限**（一定時間内の発注件数制限）あり
- **規約 第3条18項（確認済み）**: 「商品の区分（現物取引、信用取引）、執行条件（成行、指値等）の別に
  かかわらず、**同一銘柄に対しての注文は5件を上限**としてご利用ください」。v1は1日1銘柄・新規1回＋
  利確/損切り/決済で数回程度のため余裕はあるが、**訂正・取消のやり直しを繰り返すと簡単に5件に達する**。
  botのリトライ処理はこの上限を意識して設計する。`guardrails.md` の「1日の最大発注回数」に反映済み。

## 規約で確認した禁止事項・注意点（第3条・第4条）

- **第三者に使用させない**（有償無償問わず譲渡・使用許諾禁止／API・派生物の第三者利用禁止）。
  → 自分の口座のみで使う設計（`docs/decisions/0005`）と整合。bot・シグナルの外部提供はしない
- **金融商品仲介業では使用不可**（第3条15）。他人の資金を運用する事業にはできない
- **情報の再配信・転載・スクリーンスクレイピング類似行為の禁止**（第3条2）。API経由で取得した
  相場情報をnote等にそのまま転載しない（開発1部のcatalog #7-8執筆時に注意）
- **第三者が作成したプログラム等の利用禁止**（第3条17）。ネットに落ちている既製の自動売買スクリプトを
  組み込まず、自分（Claude Codeとの共同開発）で書いたコードのみを使う
- **APIの複製・逆アセンブル・改変の禁止**（第3条4・5）
- **免責が広い**（第4条）: 自作スクリプトの誤動作は**全部免責**（第4条5）。通信障害・API側の遅延・
  誤謬も基本的に会社側は無過失なら免責。→ **誤発注・バグの実害は自己責任で全額かぶる前提**で
  ガードレール・段階導入を設計する必要性の裏付け
- サービス内容は予告なしに変更・終了されうる（第5条）

## デイトレード信用取引（2026-09-12 WebSearchで確認・要一次確認）

三菱UFJ eスマート証券には、日計り専用の「**デイトレード信用取引**」という商品がある
（https://kabu.com/item/shinyo/about/deitore.html）。v1.1の設計（同日新規→同日返済）と一致。

- 返済期限は**当日中**（建玉の持ち越し不可）
- **取引手数料無料**、**金利・貸株料0%**
- 同一保証金で1日に何度でも回転売買が可能（v1.1は1日1往復のみ使用）
- **対象銘柄は当社（eスマート証券）指定銘柄のみ**。制度信用・一般信用の対象銘柄とは別のリスト。
  → botの除外条件に「デイトレード信用取引の対象銘柄かどうか」の照合を追加する必要がある
  （`stock-app`のおすすめ銘柄がこのリストに無い場合は見送り）
- 委託保証金率は**30%**（2026-09-13、三菱UFJ eスマート証券の公式資料で確認。買い建玉＋売り建玉の
  合算金額の30%が必要、これは日本の法定最低委託保証金率でもある）。`guardrails.md`のキルスイッチ額に反映済み
- 未決済のまま持ち越すと強制決済手数料が有料になる、との記載あり → 11:15の強制決済ロジックを
  確実に動かすことが特に重要
- **注意**: 検索で「国内株式の差金決済取引（日計り売買）は禁止」という情報も出てきたが、上記の
  デイトレード信用取引の存在と矛盾するため、これは別の文脈（現物取引の差金決済等）を誤って
  引用したものと判断。実際に自動売買を始める前に、eスマート証券の公式ページ・カスタマーサポートで
  最終確認することが望ましい

## 実装で気をつける（規約＋一般的な注意）

- 現物／信用で発注パラメータが異なる。**v1は信用取引（日計り）**（`strategy.md` 2026-09-12訂正）
