# トレード部 — 戦略メモ

売買の根拠をここに残す。実装は別リポの bot 本体（`投資` monorepo の `daytrade-bot/`、`stock-app` と同じ場所）。
**Claude Code / trade-ops は戦略・コードのドラフトまで。発注はしない。**

**設計の置き場所の分担**: この戦略・パラメータの「意味」の定義は Basel（このファイル・`guardrails.md`）が
持つ。実際に bot が読み込む設定ファイルの実体・売買履歴のログは `投資/daytrade-bot/`（GitHub管理）に置く
（Basel外・API認証情報と同じ理由）。このファイルの表の項目名と、daytrade-bot の設定ファイルのキー名は
一致させる。

## 全体像（v1.1・社長方針 2026-09-12。複数銘柄・成行エントリーに更新）

**1銘柄・前場だけで完結**する順張りデイトレを自動化する（購入件数は設定で複数に増やせる作りにする）。

| 時刻 | 何をする |
|---|---|
| 7:00 | `stock-app` が **おすすめ株を最大10位まで** 順位付きで選定（`recommendations`）。日によっては0件（「おすすめ無し」）もある。スコア＝直近5営業日モメンタム＋出来高急増度、フィルタ＝5日MA>20日MA・RSI14<70・直近採用済み除外 |
| 9:00〜 | bot が設定画面の条件で当日の買付銘柄を確定 → **始値が確定するのを待つ**（最大5分。kabuステーションAPIの気配/約定情報を監視） |
| 始値確定後 | 前日終値比のギャップを計算。**ギャップ許容上限以内なら成行で新規買い**（指値ではない。始値はその瞬間まで存在しないため指値を出しようがない）。**上限を超えていたら、その日は見送り**（買う前に判断・指値のように事前ブロックできる） |
| （5分待っても始値が確定しない場合） | 特別気配等で寄り付いていないと判断し、注文を出さずその日は見送る |
| 約定後 | 実際の約定価格（＝始値相当）を基準に、**利確の売り指値**（+X%）と **損切りの逆指値**（−Y%）を置く（この段階は価格が判明しているので指値/逆指値でOK） |
| 11:15ごろ（前場引けの少し前） | 利確・損切りどちらも当たっていない建玉を、**成行で決済**（v1.1は前場のみで完結・オーバーナイトなし。設定上は後場15:15決済も選べる作りにするが、当面は前場固定で運用し、実績を見てから検討） |
| 随時 | 当日の損失合計が `guardrails.md` の「1日の最大損失額」に達したら、残る建玉をすべて成行決済して当日終了（キルスイッチ） |

**エントリーが成行である理由**: 始値は寄り付きの板寄せで決まるため、寄り付き前に「始値そのもの」を指値として指定することはできない。
「始値を確認してからギャップが許容内かを判断し、許容内なら成行で買う」ことで、買う前にギャップの大きい銘柄を除外できる
（買った後に慌てて手仕舞う方式は採用しない。2026-09-12 社長と協議のうえ確定）。

## 購入条件の設定画面（`投資/daytrade-bot/` 側の実体）

毎朝9:00に bot が読み込む。値の変更は社長が行う（`docs/decisions/0005` の絶対ルール）。
**stock-appの管理画面と同じ方式**（Streamlit + Supabaseのフォーム画面）で設定する
（GitHub上のファイル直接編集ではない。2026-09-12訂正: 当初YAMLファイル方式で作ったが、
社長の想定と違ったためWeb画面に作り直した）。実体は `投資/daytrade-bot/pages/1_設定.py`、
データは Supabase の `daytrade_settings` テーブル。
`mode: log_only/paper/live` の3段階を持ち、`common/validate.py` が
paper/live 移行前に全項目確定済みかを検証し、未確定なら保存をブロックする（安全弁）。
セットアップ手順は `投資/daytrade-bot/README.md` 参照。

数値は2026-09-12に社長と確定（`guardrails.md`にも転記）。

| 項目 | 値 | 備考 |
|---|---|---|
| 購入件数（上限） | **1件** | `stock-app` の順位上位からこの件数まで採用。まずは単一銘柄で様子を見る |
| 市場フィルタ | **すべて** | 必要になれば`スタンダード／プライム／グロース`に絞る。`stock-app`の市場区分（J-Quants由来）でフィルタ |
| 1銘柄あたりの予算額 | **10万円**（初期）→ **100万円**を上限に段階増額 | 株数はここから逆算: floor(予算額÷約定価格÷100)×100株（単元株切り捨て）。100株も買えなければその日は見送り。100万円は生活防衛資金と分離した、全損しても生活に影響しない額として設定 |
| 始値確定の待機時間 | **最大5分**（9:00〜9:05） | 特別気配等でこの間に始値が確定しなければ注文を出さずその日は見送り |
| ギャップアップの許容上限 | 前日終値比 **+5%まで** | 始値確定後にこの範囲内かを判定し、範囲内なら成行で新規買い。超えていたらその日は見送り |
| 利確ライン | 約定価格 **+5%** | 指値価格は円未満を四捨五入して整数円にする。**注意**: 呼値（最小価格変動単位）は価格帯によって1円より大きい場合がある（TSEの呼値表）。単純な四捨五入だと呼値に乗らず発注が弾かれる可能性があるため、bot側で呼値表に合わせた丸めが必要か別途検証する【要確認】 |
| 損切りライン | 約定価格 **−5%** | リスクリワード1:1。同上の丸めの注意点あり。勝率5割を上回らないとコスト面で厳しくなる点は`journal/`で毎週チェック |
| 決済セッション | **前場固定**（11:15＝11:30の15分前に成行） | 実績を見てから後場(15:15)を検討。設定上はどちらも選べる作りにする |
| 1日の最大損失額（キルスイッチ） | **20,000円** | 委託保証金率が未確認のため、30%（一般的な信用取引の基準）を仮定した概算に余裕を持たせた額。確定後に見直す |
| 週の最大損失額 | **100,000円**（1日の上限×5営業日） | 到達したら週末まで停止 |
| 1日の最大発注回数 | **5回** | 規約上の同一銘柄への注文上限と同じ値。新規1＋利確/損切り1＋強制決済1が基本形で、訂正の余地は多くないため慎重に |
| 除外条件 | 決算発表日・信用取引不可・**デイトレード信用取引の対象銘柄でない**・ストップ高安・板が薄い | 「デイトレード信用取引」は当社指定銘柄のみが対象（`kabu-api-notes.md`参照）。stock-appのおすすめがこの対象銘柄かの照合が必要 |

- **順張り**である点（＝将来予測ではなく「すでに上がっている銘柄に短期で乗る」）を note/SNS でも明記する。
- エントリーは成行（上表参照）。利確/損切りは約定価格を基準にした指値/逆指値（`stock-app` の管理画面は
  前日終値基準の%だが、bot側では約定価格から再計算する）。
- **売買区分＝信用取引**。三菱UFJ eスマート証券には**「デイトレード信用取引」という同日新規→返済専用の商品**があり
  （2026-09-12確認）、取引手数料無料・金利/貸株料0%と有利。ただし**対象銘柄は当社指定銘柄に限定される**ため、
  botの除外条件に「デイトレード信用取引の対象銘柄かどうか」の照合を追加する（`kabu-api-notes.md`）。
  委託保証金率はデイトレード信用取引の専用ページに明記が無く、社長に確認を依頼中（一般的な信用取引は30%）。
  追証ライン・制度信用/一般信用の別は引き続き`guardrails.md`で管理。

## 売買履歴の置き場

`投資/daytrade-bot/` 側にログ（GitHub管理・社長がいつでも確認できる）。Basel の `trade/journal/` には
**週次・月次のサマリ**（勝率・損益・気づき）だけを記録し、生ログは持ち込まない（実装は daytrade-bot 側）。

## bot 側でも二重チェックする除外

- ストップ高/安の張り付き・値幅制限で買えない/売れない
- 当日が決算発表日の銘柄
- 気配・板が薄く指値が通らない
- 前日終値と始値の乖離が大きすぎる（ギャップアップしすぎ＝寄り天リスク。閾値は `guardrails.md`）
- 信用取引不可の銘柄（`guardrails.md`）

## v1.1 の数値（2026-09-12 確定。`guardrails.md`参照）

購入件数・予算額・エントリー方式・利確損切り・決済セッション・リスク上限・除外条件は上表の通り確定した。

  確定後に数値を見直す）
- 指値価格の呼値対応（技術的な実装課題として残る）
- 市場フィルタは「すべて」から始め、必要になったら絞る

## 検証（未実施・社長が段階導入）

- v1.1 はバックテストせず、**発注しないログモード**で数日 →
  **kabuステーションの検証用APIパスワードでの試験発注**（本番資金を動かさずに注文コードパスを確認。
  `kabu-api-notes.md` 参照）→ 最小ロット・少ない購入件数（例: 1件）で本番実発注 → 徐々に件数を増やす、と段階導入。
- kabuステーションの「ソフトリミット」を（予算額×購入件数）に見合う額まで下げてから本番に入る（`guardrails.md`）。
- 記録は `trade/journal/YYYY-MM.md`。想定（シグナルどおり動いたか）と実績（滑り・約定率・損益）を分けて書く。
- `stock-app` 側にすでに「月次勝率」があるので、bot の実損益とアプリの理論勝率の乖離を毎週見る。
